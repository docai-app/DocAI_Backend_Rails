# 微信小程序登录与账号绑定 — 可执行实施方案

**文档日期**：2026-05-11  
**适用范围**：`DocAI_Backend_Rails` — `GeneralUser`（邮箱密码 + Devise JWT）  
**状态**：待评审确认后再实施编码  

---

## 1. 背景与目标

### 1.1 现状

- 用户通过 **邮箱 + 密码** 登录，`GeneralUser` 使用 Devise（`:database_authenticatable`, `:jwt_authenticatable`），会话由 JWT 承载（参见 `config/initializers/devise.rb`、`GeneralUsers::SessionsController`）。
- `general_users` 表已有 `email`（唯一）、`meta`（jsonb）等字段。

### 1.2 业务目标

1. 用户可在 **微信小程序内嵌 WebView** 访问站点，仍先用 **邮箱 + 密码** 登录（流程不变）。
2. 登录成功后，用户授权小程序拿到 **`code`**，后端完成与微信账号的 **绑定**，以便后续 **仅凭小程序登录码快速登录**。
3. **不修改** 既有邮箱密码登录接口行为；**新增** 专用小程序登录 API。

### 1.3 重要概念澄清（实现前必须与产品对齐）

| 概念 | 说明 |
|------|------|
| **`code`（登录凭证）** | 小程序 `wx.login()` 返回，**有效期约 5 分钟**，**只能使用一次**。服务端调用微信 `jscode2session` 换取 `openid` / `session_key` 等。 |
| **不可长期保存 `code` 用于下次登录** | 下次登录必须重新 `wx.login()` 获取 **新** `code`。库存 “旧 code” 无法再次鉴权。 |
| **应持久化的是 `openid`（及可选 `unionid`）** | `openid` 在同一小程序（同一 `appid`）下对用户唯一，用于绑定到 `GeneralUser`。 |
| **`session_key`** | 会轮换，**不建议作为长期登录凭据写入数据库**；本方案**不包含**手机号解密等能力，一般不在 `meta` 中持久化 `session_key`。 |

**结论**：需求中「保存授权的 code」在工程上应落实为：**保存微信返回的稳定标识（openid / unionid）及绑定元数据**；`code` 仅在单次请求链路中用于换取会话信息。

## 2. 补充需求建议（完善原需求「3、。。。」）

建议在方案中一并覆盖：

3. **绑定策略**：一个微信 `openid` 仅绑定一个 `GeneralUser`。**本期不支持更换绑定微信**（不提供解绑 / 换绑接口；已绑定用户重复调用绑定接口时：若仍为同一 `openid` 可幂等返回成功；若试图换绑不同微信则 **拒绝**）。同一用户重复绑定同一账号仅更新可选资料字段即可。
4. **安全**：接口限流、防枚举、`appid` + `secret` 仅服务端持有；日志中禁止打印 `secret`、`session_key`、完整 `code`。
5. **与 JWT 一致**：小程序登录成功后的响应格式与现有登录一致（HTTP Header 中的 JWT、JSON body 结构约定），前端 WebView 无需两套 token 协议。
6. **可观测性**：绑定 / 登录失败原因结构化错误码，便于小程序端提示与后台排查。
7. **合规与隐私**：若存储微信昵称、头像，需在小程序隐私协议与用户授权范围内；最小化存储字段。
8. **多小程序扩展**：若未来多个小程序共用同一用户体系，应用 **`unionid`**（需开放平台绑定）或 **`app_id` + openid** 联合唯一。

## 3. 数据模型设计（`general_users.meta`）

**本期不新建独立表**，微信绑定信息保存在现有 **`general_users.meta`**（jsonb）中，与 `aienglish_role` 等字段并列，使用 **固定命名空间键**，避免与现有 `meta` 用途冲突。

### 3.1 推荐结构：`meta["wechat_miniprogram"]`

示例（字段均可按需裁剪）：

```json
{
  "wechat_miniprogram": {
    "wechat_app_id": "<与 ENV 一致，便于审计>",
    "openid": "<必填，登录与冲突检测依据>",
    "unionid": "<可选>",
    "nickname": "<可选>",
    "avatar_url": "<可选>",
    "bound_at": "<ISO8601 字符串或沿用项目 meta 时间约定>",
    "last_login_at": "<可选，最近一次小程序 JWT 登录成功时间>",
    "extra": {}
  }
}
```

**约定**：

- **不要** 在 `meta` 中长期保存 `code`、`session_key`。
- `openid` + `wechat_app_id` 在业务上应全局唯一；因无独立表唯一索引，**必须在绑定与登录逻辑中显式校验**：
  - 绑定时：查询是否已有 **其他** `GeneralUser` 的 `meta->wechat_miniprogram->openid`（及同 `wechat_app_id`）等于本次换得的 openid → 有则 `WECHAT_OPENID_CONFLICT`。
  - 小程序登录时：按 `openid`（及 `wechat_app_id`）反查用户。
- **性能（可选，上线后若量大再做）**：可增加 PostgreSQL **表达式索引**，例如对 `(meta #>> '{wechat_miniprogram,openid}')` 建唯一索引（需与空值、历史脏数据治理一并评估）。

### 3.2 模型层实现建议（`GeneralUser`）

- 使用 **`store_accessor :meta, ...`** 不直接适用嵌套键时，可封装方法：`wechat_miniprogram_binding`、`bind_wechat_miniprogram!(...)`, `wechat_miniprogram_bound?`，内部读写 `meta['wechat_miniprogram']`。
- 或在 **`GeneralUser` 的 concern**（如 `HasWechatMiniprogramBinding`）中集中维护读写与校验，保持控制器精简。

### 3.3 换绑与解绑（本期范围）

- **不支持** 用户主动更换绑定的微信账号（不提供解绑、不提供「覆盖绑定」为新 openid）。
- 若已存在 `meta.wechat_miniprogram.openid`，再次 `bind` 时仅当 `code` 换得的 openid **与已存一致** 时允许成功（幂等）；**不一致** 则返回错误（如 `WECHAT_ALREADY_BOUND`），提示联系客服或沿用当前约定。

## 5. 后端服务层：`WechatMiniprogram::AuthService`（建议）

职责拆分：

1. **`exchange_code(code)`**  
   - `GET https://api.weixin.qq.com/sns/jscode2session`  
   - 参数：`appid`, `secret`, `js_code`, `grant_type=authorization_code`  
   - 返回：`openid`, `session_key`, `unionid`（可选）、`errcode`  
   - **错误处理**：微信返回非 0 时抛出带 `errcode` 的业务异常，映射为统一错误响应。

2. **`bind!(general_user:, code:, profile: {})`**（仅在用户已邮箱登录态下调用）  
   - `exchange_code` → 得到 `openid`  
   - 若当前用户 **已有** `meta.wechat_miniprogram.openid` 且与本次 openid **不一致** → **拒绝**（不换绑）  
   - 检查 `openid` 是否已被 **其他** 用户写入 `meta` → 冲突则拒绝  
   - 写入或幂等更新 `meta["wechat_miniprogram"]`（含可选 `profile`）  

3. **`login_with_code(code)`**（未登录态）  
   - `exchange_code` → `openid` → 查询 **哪位用户的 `meta`** 含该 openid → 得到 `GeneralUser`  
   - 若未绑定 → 返回明确错误（引导用户先邮箱登录再绑定）  
   - 调用与 Devise JWT 一致的签发流程（见第 7 节），更新 `meta` 内 `last_login_at`  

**HTTP 客户端**：使用 `Faraday` / `Net::HTTP`；设置合理超时（如 5s）；对微信接口失败做重试策略需谨慎（通常不重试或仅一次）。

## 6. API 设计（新增，不改变原有路由）

以下路径置于 `namespace :api` → `namespace :v1` 下（具体前缀与现有风格对齐，例如 `/api/v1/...`）。

### 6.1 绑定微信（需在邮箱登录后，携带 JWT）

| 项目 | 说明 |
|------|------|
| **Method / Path** | `POST /api/v1/general_users/wechat_miniprogram/bind` |
| **认证** | `Authorization: Bearer <JWT>`（与现有 `authenticate_general_user!` 一致） |
| **Body（JSON）** | `{ "code": "<wx.login 返回>", "nickname": "可选", "avatar_url": "可选" }` |
| **成功** | `{ success: true, binding: { wechat_app_id, openid, unionid, bound_at } }`（**勿**返回 session_key） |
| **失败示例** | `openid` 已被他人占用；微信 `code` 无效或过期；**已绑定其他 openid 后试图换绑** |

### 6.2 微信小程序专属登录（未登录态）

| 项目 | 说明 |
|------|------|
| **Method / Path** | `POST /api/v1/general_users/wechat_miniprogram/login` |
| **认证** | 无（或仅服务端防火墙 / IP 策略） |
| **Body** | `{ "code": "<wx.login 返回>" }` |
| **成功** | 与现有 `GeneralUsers::SessionsController#login_success` 对齐：**HTTP 状态 200**，且响应头中包含 JWT（Devise-JWT 默认行为需确认是否与邮箱登录一致）；Body 建议 `{ success: true, message: "..." }`。若项目 JWT 仅放在 Header，文档中写明前端从 Header 读取。 |
| **失败** | 未绑定：`401` 或 `404` + 统一错误码，例如 `WECHAT_NOT_BOUND`，提示用户先在网页邮箱登录并绑定 |

### 6.3 可选：查询绑定状态（已登录）

| 项目 | 说明 |
|------|------|
| **Method / Path** | `GET /api/v1/general_users/wechat_miniprogram/binding` |
| **认证** | JWT |
| **响应** | 是否已绑定、`bound_at`、`last_login_at`（**不**返回 secret） |

### 6.4 解绑 / 换绑

**本期不提供**（与「不支持更换绑定微信」一致）。后续若开放，需单独方案（含风控与客服流程）。

## 7. 与 Devise JWT 集成要点

当前邮箱登录使用 `Devise::SessionsController`，JWT 由 `devise-jwt` 根据 `dispatch_requests` 下发（参见 `config/initializers/devise.rb`）。

**实施时有两种等价路径（二选一，需在编码阶段确认现有配置）：**

- **方案 A**：在新控制器中手动 `sign_in(resource)` 并依赖 Warden/Devise-JWT 的同路径派发 JWT（需匹配 `jwt.dispatch_requests` 中的 path/method）。  
- **方案 B**：不经过 SessionController，直接调用与登录相同的 JWT 签发逻辑（若项目已有封装）。  

**验收标准**：小程序登录成功后，获得的 JWT 与邮箱登录在 **格式、`Authorization` 用法、`jwt_payload`** 上一致，现有 `ApiController` 中 `authenticate_general_user!` **无需区分登录来源**。

## 9. 小程序端流程（WebView / 原生容器）

### 9.1 首次使用（未绑定）

1. WebView 内走现有邮箱密码登录 → 拿到 JWT。  
2. 小程序调用 `wx.login()` → 将 `code` POST 到 **`bind`** 接口（Header 带 JWT）。  
3. 后端换 `openid` 并写入该用户的 `meta["wechat_miniprogram"]`。

### 9.2 再次进入（已绑定）

1. `wx.login()` → `code` POST 到 **`login`** 接口。  
2. 后端换 `openid`，按 `meta` 反查用户 → 签发 JWT → WebView 带上 token 访问业务页。

## 10. 错误码与 HTTP 状态约定（建议）

| 场景 | HTTP | `error_code`（示例） |
|------|------|---------------------|
| 微信 `code` 无效 / 过期 | 401 | `WECHAT_CODE_INVALID` |
| 未绑定 openid | 404 或 401 | `WECHAT_NOT_BOUND` |
| openid 已被其他账号绑定 | 409 | `WECHAT_OPENID_CONFLICT` |
| 已绑定微信且尝试换绑（openid 不一致） | 409 | `WECHAT_ALREADY_BOUND` |
| 微信服务端临时故障 | 502 / 503 | `WECHAT_UPSTREAM_ERROR` |
| 限流 | 429 | `RATE_LIMITED` |

## 11. 测试计划

- Model / Service：绑定冲突（两用户同 openid）；**已绑定用户换绑第二微信号应失败**；同用户同 openid 幂等。  
- Service：mock `jscode2session` 响应（成功 / errcode 40029 invalid code）。  
- Request：`bind` 需 JWT；`login` 无 JWT；绑定后 `login` 返回 JWT。  
- 安全：`app_secret` 不出现在响应与日志。
