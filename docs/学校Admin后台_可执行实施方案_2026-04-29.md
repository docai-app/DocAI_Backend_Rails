# 学校 Admin 后台可执行实施方案

## 1. 目标

在现有 `AIEnglish Admin Dashboard` 基础上，新增一套专门给每所学校老师 / 学校管理员使用的后台系统。

这套后台的目标是：

- 让学校方可以查看自己学校内的学生、老师、assignment 和提交记录
- 让学校方可以重设学生密码
- 不开放高风险操作，例如 `rerun`
- 保持界面简洁，风格尽量接近 `AI English`
- 所有关键操作都要有 log 记录

这套系统不是现有总管理后台简单加几个按钮，而是需要明确区分：

1. 平台总管理后台
2. 学校级后台

## 2. 角色定义

### 2.1 `super_admin`

平台内部管理员，使用现有 `AIEnglish Admin Dashboard`。

权限：

- 创建学校
- 管理学校资料
- 创建 `school_admin` 账号
- 绑定 `school_admin` 到指定学校
- 查看所有学校资料
- 查看所有 assignment / submission
- 查看所有 logs

### 2.2 `school_admin`

学校级管理员，使用新的学校后台。

权限：

- 只能看自己学校的数据
- 可以查看本校所有老师创建的 assignments
- 可以点开 assignment
- 可以点开 assignment 下每一条学生 submission
- 可以查看单一学生的作业详情
- 可以重设学生密码
- 可以查看本校操作 logs

限制：

- 不可以 rerun
- 不可以删除 assignment
- 不可以编辑平台级设置
- 不可以查看其他学校数据
- 不可以创建学校
- 不可以管理其他学校账号

## 3. 网站与入口规划

建议将学校后台与总管理后台分开。

### 推荐方案：不同子网域

- 总管理后台：`admin.docai.net`
- 学校后台：`school-admin.docai.net`

优点：

- 角色边界清楚
- 权限隔离更安全
- 用户心智模型明确
- 后续扩展更容易

### 备选方案：同站不同入口

- 总管理后台：`/admin/...`
- 学校后台：`/school-admin/...`

如果短期部署成本较高，可以先这样做，但长期还是建议拆分入口。

## 4. 产品范围

第一版的学校后台建议只做以下核心模块：

1. 登录页
2. Dashboard
3. Students
4. Assignments
5. Submission Detail
6. Operation Logs

## 5. 页面结构

### 5.1 登录页

用途：

- 学校 admin 使用单独账号登录

要求：

- 与 `AI English` 风格接近
- 页面简洁
- 不显示平台级入口

字段：

- Email
- Password

行为：

- 登录成功后进入学校后台首页
- 登录后只能访问自己学校的数据

### 5.2 Dashboard

用途：

- 展示学校层级总览

建议内容：

- 学校名称
- 学生总数
- 老师总数
- assignment 总数
- 最近提交数
- 最近操作记录

设计原则：

- 简洁
- 重点是快速概览
- 不需要太多复杂图表

### 5.3 Students

用途：

- 查看本校学生
- 搜寻学生
- 重设密码

建议字段：

- Student Name
- Email
- Class
- Student Number
- Status
- Updated At

操作：

- View
- Reset Password

### 5.4 Assignments

用途：

- 查看本校所有老师创建的 assignments

筛选条件建议：

- Teacher
- Assignment Category
- Created Date
- Status

列表字段建议：

- Assignment Title
- Topic
- Category
- Creator
- Created At
- Submission Count
- Status

操作：

- View Assignment
- View Submissions

限制：

- 不显示 `rerun`
- 不显示高风险操作按钮

### 5.5 Assignment Detail

用途：

- 查看单一 assignment 详情

内容建议：

- Assignment 基本资料
- 创建老师
- 类别
- 创建时间
- 提交数量
- 状态统计
- 学生 submissions 列表

操作：

- 只能查看
- 可以点开每一条 submission

### 5.6 Submission Detail

用途：

- 点开单一学生作业详情

内容建议：

- Student 基本信息
- Submission 时间
- Submission 内容
- Status
- Score
- AI feedback / grading detail
- 相关附件或报告链接（如果后端已提供）

限制：

- 只读
- 不可 rerun
- 不可更改评分流程

### 5.7 Operation Logs

用途：

- 查看学校后台关键操作记录

列表字段建议：

- Operator
- Action
- Target Type
- Target Name / ID
- Time
- IP

## 6. 密码重设规则

第一版规则如下：

- `school_admin` 点击 `Reset Password`
- 系统直接将该学生密码重设为 `12345678`
- 第一版先不做 `must_change_password`
- 操作必须写入 log

### 第一版不做

- 不强制学生首次登录改密码
- 不支持自定义重设密码
- 不支持学校 admin 输入自定义密码

### 建议的前端行为

- 点击 `Reset Password`
- 弹出确认视窗
- 提示：
  - “This student password will be reset to 12345678.”
- 确认后执行
- 成功后显示 toast

## 7. 权限矩阵

### `school_admin` 可以

- 查看本校 students
- 搜寻本校 students
- 重设本校学生密码
- 查看本校 teachers
- 查看本校 assignments
- 查看 assignment detail
- 查看 submissions list
- 查看单一学生 submission detail
- 查看本校操作 logs

### `school_admin` 不可以

- 查看其他学校数据
- 修改老师密码
- rerun assignment
- 删除 assignment
- 编辑平台级参数
- 创建学校
- 删除学校
- 管理其他 `school_admin`

## 8. 操作日志设计

### 8.1 必须记录的事件

- `school_admin_signed_in`
- `school_admin_signed_out`
- `student_password_reset`
- `student_viewed`
- `assignment_list_viewed`
- `assignment_viewed`
- `submission_viewed`

### 8.2 建议 log 字段

- `id`
- `actor_id`
- `actor_role`
- `school_id`
- `action`
- `target_type`
- `target_id`
- `metadata`
- `ip_address`
- `user_agent`
- `created_at`

### 8.3 `student_password_reset` 的 metadata 建议

```json
{
  "reset_to_default_password": true,
  "default_password_label": "12345678"
}
```

注意：

- 不要在 log 中保存明文密码

## 9. 前端实施建议

### 9.1 建议新增独立模块

建议在现有 admin dashboard repo 中新增一套 `school admin portal` 页面结构，而不是把所有逻辑硬塞进原本页面。

建议结构示意：

```text
app/
  school_admin/
    login/
    dashboard/
    students/
    assignments/
    assignments/[id]/
    submissions/[id]/
    logs/
```

### 9.2 UI 原则

- 风格接近 `AI English`
- 导航简洁
- 控件清楚
- 少量但明确的卡片与表格
- 优先信息可读性

建议左侧导航：

- Overview
- Students
- Assignments
- Logs
- Profile / Logout

### 9.3 可复用现有模块

现有 repo 中已有不少内容可复用：

- 学校数据结构
- 老师 / 学生管理 API
- assignment management 列表与详情模式
- activity logs 展示方式

可参考现有页面：

- `app/school_management/page.tsx`
- `app/assignment_management/page.tsx`
- `components/assignment/AssignmentsList.tsx`
- `components/UserActivityLogs.tsx`

但需要做 school-scoped 版本，而不是直接复用原页面。

## 10. 后端需求

这个功能不能只做前端，backend 必须支持。

### 10.1 账号与权限

需要支持：

- `school_admin` 角色
- `school_admin` 绑定 `school_id`
- 登录后只返回该角色可访问的数据

### 10.2 建议新增 / 调整的 API 能力

#### A. School admin account management

给 `super_admin` 用：

- 创建 `school_admin`
- 更新 `school_admin`
- 停用 / 启用 `school_admin`

示意：

- `POST /api/admin/v1/school_admins`
- `PATCH /api/admin/v1/school_admins/:id`
- `GET /api/admin/v1/school_admins`

#### B. School admin login

给学校后台使用：

- 登录
- 获取当前 school admin profile

示意：

- `POST /api/school_admin/v1/sign_in`
- `GET /api/school_admin/v1/me`

#### C. School-scoped students

- `GET /api/school_admin/v1/students`
- `GET /api/school_admin/v1/students/:id`
- `POST /api/school_admin/v1/students/:id/reset_password`

#### D. School-scoped assignments

- `GET /api/school_admin/v1/assignments`
- `GET /api/school_admin/v1/assignments/:id`
- `GET /api/school_admin/v1/assignments/:id/submissions`
- `GET /api/school_admin/v1/submissions/:id`

注意：

- 不返回 rerun action
- 不提供 rerun endpoint 给 `school_admin`

#### E. Operation logs

- `GET /api/school_admin/v1/logs`

### 10.3 数据隔离要求

所有 `school_admin` 接口必须基于 `school_id` 强制做数据隔离：

- 只能访问当前学校
- 即使前端传其他学校 ID，也必须被后端拦住

## 11. Assignment 查看范围定义

`school_admin` 不只是看 assignment 列表，还要可以完整 drill-down：

1. Assignment List
2. Assignment Detail
3. Submission List
4. Single Submission Detail

也就是说：

- assignment 的每一条记录都可以点开
- assignment 下每一个学生 submission 都可以点开
- 可以看到单一学生作业详情

但是：

- 只读
- 不可以 rerun

## 12. 推荐实施顺序

### Phase 1

- `school_admin` 账号模型与登录
- 学校后台 layout
- Students 页面
- Reset Password
- Logs 页面

### Phase 2

- Assignments List
- Assignment Detail
- Submission List
- Submission Detail

### Phase 3

- 更完整 Dashboard
- 更丰富统计筛选
- 后续再考虑更细的权限扩展

## 13. 第一版明确不做

为了避免第一版范围失控，以下内容先不做：

- `must_change_password`
- 学生首次登录强制改密码
- 学校 admin 自定义新密码
- rerun
- assignment 删除
- assignment 编辑
- 老师密码重设
- 跨学校查看
- 复杂报表导出

## 14. 验收标准

第一版完成的标准建议如下：

1. `super_admin` 可以在总后台创建 `school_admin`
2. `school_admin` 可以登录单独后台
3. 登录后只能看到自己学校的数据
4. `school_admin` 可以查看本校 students 列表
5. `school_admin` 可以将任一学生密码重设为 `12345678`
6. 重设密码操作会写入 log
7. `school_admin` 可以查看本校所有老师创建的 assignments
8. `school_admin` 可以点开 assignment detail
9. `school_admin` 可以点开 assignment 下的 submission
10. `school_admin` 可以查看单一学生 submission detail
11. 全流程中不存在 `rerun` 能力
12. 所有查看与重设密码关键操作均有 audit log

## 15. 建议结论

这是一个值得做、而且应该独立做的模块。

推荐方向：

- 保留现有总管理后台给平台内部团队
- 新增一套独立的学校后台给学校 admin
- 第一版重点放在：
  - 学生密码重设
  - assignment / submission 只读查看
  - 操作日志

这样可以最快满足学校实际管理需求，同时把风险控制在较小范围内。

## 16. 前端第二阶段接入方案

目前前端已经先完成可预览版本，并加入一层资料来源切换。

默认状态：

- 使用本机 `localStorage` mock data
- 方便先确认 UI、流程、权限边界和操作日志
- 不依赖 backend 是否已经完成

切换到真实 API：

- 在环境变量加入 `NEXT_PUBLIC_SCHOOL_ADMIN_PORTAL_DATA_SOURCE=api`
- 前端会从 mock data 改为调用 `apis/schoolAdminPortal.ts`
- 页面和组件不需要重写

当前前端已经预留的 API：

- `GET /api/admin/v1/school_admin_accounts`
- `POST /api/admin/v1/school_admin_accounts`
- `PATCH /api/admin/v1/school_admin_accounts/:id/toggle_status`
- `POST /api/school_admin/v1/session`
- `DELETE /api/school_admin/v1/session`
- `GET /api/school_admin/v1/snapshot`
- `POST /api/school_admin/v1/students/:id/reset_password`
- `POST /api/school_admin/v1/audit_logs`

其中 `GET /api/school_admin/v1/snapshot` 建议一次返回学校后台首页所需的 school-scoped 数据：

```json
{
  "success": true,
  "data": {
    "school": {},
    "students": [],
    "teachers": [],
    "assignments": [],
    "submissions": [],
    "logs": []
  }
}
```

这样做的原因：

- 学校后台第一版页面不复杂，一次性拿 school-scoped snapshot 会比较稳定
- 后续如果数据量变大，可以再拆成 students、assignments、logs 分页 API
- 前端现在已经通过 `hooks/useSchoolAdminPortal.ts` 统一读取资料，后续拆 API 时页面不需要大改

backend 需要特别保证：

- `school_admin` 登录后只能拿到自己学校的数据
- `snapshot` 不返回其他学校资料
- reset password 固定重设为 `12345678`
- 第一版不做 `must_change_password`
- reset password 和查看操作都要写入 audit log
- assignment 和 submission 只读，不开放 rerun
